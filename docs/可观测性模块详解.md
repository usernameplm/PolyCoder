# 可观测性模块详解（零基础向）

> 面向对象：没用过 `structlog` / `prometheus_client` / `opentelemetry` 这三个库的读者。
> 目标：看完这篇文档，能说清楚——本项目里"观测"到底是什么、代码怎么记录数据、数据存在哪、怎么查。

---

## 0. 先建立一个直觉：什么是"可观测性"

假设你的 Agent 服务上线后，用户在群里说："机器人刚才半天没回我"。你打开电脑，只有一句话能查："服务好像在跑"（因为 `curl /health` 返回了 `{"status": "ok"}`）。除此之外你一无所知：

- 那个用户的请求到底进来了没有？
- 卡在哪一步？调用 LLM 慢，还是某个工具执行慢？
- 是不是有很多请求同时堆积，把 Agent 拖垮了？
- 这一分钟内出错的请求有多少？

"可观测性"（Observability）就是提前在代码里埋好"探针"，让你不用临时加 `print()` 重新部署，就能回答上面这些问题。业界通常分成三个维度，本项目也正好对应三个模块：

| 维度 | 本项目对应文件 | 用的库 | 一句话回答的问题 |
|------|--------------|--------|-----------------|
| 日志（Logging） | `observability/logging.py` | `structlog` | "这一次具体发生了什么事？"（事件级别，看单条记录） |
| 指标（Metrics） | `observability/metrics.py` | `prometheus_client` | "整体健康状况怎样？"（统计级别，看趋势和数字） |
| 追踪（Tracing） | `observability/tracing.py` | `opentelemetry` | "一个请求内部，时间都花在哪一步？"（链路级别，看时间轴） |

三者不是互相替代关系，是互补的：日志告诉你"发生了什么"，指标告诉你"发生了多少/多快"，追踪告诉你"发生的顺序和耗时分布"。下面逐个拆解。

## 1. 日志：`structlog`

### 1.1 为什么不直接用 `print()` 或 Python 自带的 `logging`

`print("用户问了：", question)` 能用，但有个根本问题：**它是给人看的一句话，不是给机器解析的数据**。

如果你想统计"这一小时里 `session_id=abc123` 的所有日志"，用 `print` 打出来的文本，你只能用眼睛去日志文件里翻，或者写一堆脆弱的正则表达式去匹配文本格式。一旦某个人多加了一个空格、换了个词的顺序，正则就失效了。

`structlog` 的核心思路是：**每条日志不是一句话，而是一个"事件名 + 一堆 key-value 字段"的结构化记录，最终序列化成 JSON**。JSON 是机器最容易解析的格式——不管是 Grafana Loki、ELK，还是你自己写个脚本用 `json.loads()` 一行行读，都能精确地按字段过滤、聚合、画图。

### 1.2 代码逐行解释：`observability/logging.py`

```python
import structlog
import logging


def setup_logging(log_level: str = "INFO"):
    """初始化结构化日志，在服务启动时调用一次。"""

    logging.basicConfig(
        level=getattr(logging, log_level.upper()),
        format="%(message)s",
    )

    structlog.configure(
        processors=[
            structlog.stdlib.add_log_level,
            structlog.processors.TimeStamper(fmt="iso"),
            structlog.processors.StackInfoRenderer(),
            structlog.processors.format_exc_info,
            structlog.processors.JSONRenderer(ensure_ascii=False),
        ],
        wrapper_class=structlog.make_filtering_bound_logger(logging.INFO),
        context_class=dict,
        logger_factory=structlog.PrintLoggerFactory(),
    )


logger = structlog.get_logger()
```

先说结论：这个文件只做一件事——**配置好一套"日志加工流水线"，然后导出一个全局 `logger` 对象供其他文件 `import` 使用**。逐块看：

**`logging.basicConfig(...)`**

这一行配置的是 Python **标准库**的 `logging` 模块（跟 `structlog` 是两套东西，`structlog` 只是在标准库之上再包一层）。这里其实作用不大——因为下面 `structlog.configure()` 里用的是 `PrintLoggerFactory()`（直接 `print`，完全绕开了标准库的 handler 机制），这行主要是保证如果项目里其他第三方库内部用了标准 `logging`，它们的输出格式也是干净的（`format="%(message)s"` 表示不加时间戳等前缀，因为 `structlog` 自己会加）。

**`structlog.configure(processors=[...])` —— "流水线"是什么意思**

`structlog` 的核心机制：你写 `logger.info("agent_loop_turn", turn=2, tokens=100)` 时，`structlog` 不会立刻把这条日志打印出来，而是先组装成一个字典（叫 `event_dict`）：

```python
{"event": "agent_loop_turn", "turn": 2, "tokens": 100}
```

然后**依次**把这个字典喂给 `processors` 列表里的每一个函数，每个函数可以往字典里加字段、改字段，或者直接把它渲染成最终字符串。列表里的顺序就是执行顺序：

1. `structlog.stdlib.add_log_level` —— 往字典里加一个 `"level": "info"` 字段。
2. `structlog.processors.TimeStamper(fmt="iso")` —— 加一个 ISO 格式的时间戳字段，比如 `"timestamp": "2026-07-10T08:07:00.230615Z"`。
3. `structlog.processors.StackInfoRenderer()` —— 如果调用时传了 `stack_info=True`，把调用栈信息加进去（正常日志不会触发，用于调试）。
4. `structlog.processors.format_exc_info` —— 如果调用时传了 `exc_info=True`（比如在 `except` 块里），把异常的 traceback 格式化后加进字典。
5. `structlog.processors.JSONRenderer(ensure_ascii=False)` —— **流水线的最后一步**，把整个字典序列化成一行 JSON 字符串。`ensure_ascii=False` 是关键：默认 `json` 库会把中文转成 `\uXXXX` 转义序列，加这个参数才能让日志里的中文正常显示，不然你会看到一堆看不懂的 `你好`。

跑完这条流水线，字典变成了这样一行文本：

```json
{"event": "agent_loop_turn", "turn": 2, "tokens": 100, "level": "info", "timestamp": "2026-07-10T08:07:00.230615Z"}
```

**`wrapper_class=structlog.make_filtering_bound_logger(logging.INFO)`**

这个负责"日志级别过滤"——如果代码里调用了 `logger.debug(...)`，但这里配置的级别是 `INFO`，那么这条 `debug` 日志会在最早期就被直接丢弃，连流水线都不会跑（性能更好）。级别顺序是 `DEBUG < INFO < WARNING < ERROR`，设成 `INFO` 意味着 `INFO` 及以上（`INFO`/`WARNING`/`ERROR`）都会被记录，`DEBUG` 会被忽略。

**`logger_factory=structlog.PrintLoggerFactory()`**

流水线跑完，字符串已经生成好了，谁来负责真正把它输出出去？答案由 `logger_factory` 决定。`PrintLoggerFactory()` 意味着"直接调用 Python 的 `print()`，打到标准输出（stdout）"。这也是为什么前面 `logging.basicConfig()` 配的标准库 handler 基本没用上——这条日志压根没走标准库那一套，是自己直接 `print` 出去的。

> 为什么选择直接 `print` 而不是走标准库？因为部署到容器（Docker/K8s）里时，标准做法是把 stdout 收集起来（比如用 `docker logs` 或者云厂商的日志服务自动采集容器 stdout），不需要应用自己去写文件、做日志切割——写到 stdout 就够了，最简单。

**`logger = structlog.get_logger()`**

这行代码创建了一个全局的 logger 实例，注意它必须写在 `setup_logging()` 函数**外面**（模块顶层），这样别的文件 `from observability.logging import logger` 拿到的就是同一个对象。但要注意一个关键点：**`get_logger()` 拿到的 logger，行为取决于"调用它的时候" `structlog.configure()` 有没有生效**——`structlog` 的配置是全局单例的，`setup_logging()` 不调用，`logger` 也能用，只是走的是 structlog 内置的默认配置（不是 JSON，样子会很不一样）。

### 1.3 一个真实踩过的坑：`filter_by_level` / `add_logger_name` 不能配 `PrintLoggerFactory`

这份代码原本的 `processors` 列表里还有两行：

```python
structlog.stdlib.filter_by_level,
structlog.stdlib.add_logger_name,
```

这两个 processor 名字带 `stdlib`，意思是"专门配合标准库 `logging.Logger` 使用的"——`filter_by_level` 内部要读 `logger.disabled` 属性来判断是否要过滤，`add_logger_name` 要读 `logger.name` 属性来记录是哪个 logger 打的。但我们这里 `logger_factory` 用的是 `PrintLoggerFactory()`，它产出的 `PrintLogger` 对象根本没有 `.disabled` 和 `.name` 这两个属性——这是两套不同的 logger 实现，硬凑在一起用。

结果就是：只要真的调用一次 `logger.info(...)`，流水线跑到这两个 processor 就会直接抛异常：

```
AttributeError: 'PrintLogger' object has no attribute 'disabled'
```

**更麻烦的是，这个 bug 是"潜伏"的**——只要没人调用 `setup_logging()`，`structlog.configure()` 就不会生效，用的是默认配置（不会走到这两个坑），代码看起来完全正常，`python -m py_compile` 也不会报任何错。这个 bug 只有在服务真正启动、`setup_logging()` 被调用、并且有人第一次调用 `logger.info(...)` 时才会炸出来。

修复方式很简单：既然日志级别过滤已经交给了 `wrapper_class=structlog.make_filtering_bound_logger(logging.INFO)`，`filter_by_level` 就是多余的；`add_logger_name` 只是加个字段，不加也不影响核心功能——直接从 `processors` 列表里删掉这两行即可。

**这条教训背后更通用的道理**：`structlog` 高度可配置，几乎每个 processor 单独看都写得没问题，但**它们对"底层 logger 是什么类型"有隐含假设**，混用不同套路的 processor（`stdlib.*` 系列 vs `PrintLoggerFactory`）容易凑出这种只在运行时才暴露的兼容性 bug。写完配置后，最好实际调用一次 `logger.info(...)` 验证，而不是只看它能不能 import 成功。

### 1.4 全项目怎么用这个 `logger`

任何文件只要这样写：

```python
from observability.logging import logger

logger.info("agent_loop_turn", session_id="user_001", turn=2, tool_calls=["calculator"])
```

就会输出（前提是 `setup_logging()` 已经在启动时调用过）：

```json
{"event": "agent_loop_turn", "session_id": "user_001", "turn": 2, "tool_calls": ["calculator"], "level": "info", "timestamp": "2026-07-10T08:07:00Z"}
```

`session_id`、`turn`、`tool_calls` 都是你随手传的关键字参数，`structlog` 不需要你提前"注册"这些字段名，想加什么字段直接传就行——这就是"结构化"的意思：字段是数据，不是拼接在一句话里的文本。

还有一个常用技巧：`logger.bind(session_id=req.session_id)`。这会返回一个新的 logger，之后这个新 logger 打的每一条日志都自动带上 `session_id` 字段，不用每次手写：

```python
log = logger.bind(session_id=req.session_id)
log.info("ask_request_received", question=req.question[:60])
log.info("ask_request_done", elapsed_ms=elapsed_ms)
# 两条日志都自动带着同一个 session_id，方便按会话把日志串起来看
```

本项目 `main.py` 的 `/ask` 接口正是这么用的。

## 2. 指标：Prometheus (`prometheus_client`)

### 2.1 指标和日志的本质区别

日志是"一条一条的事件记录"，量大、细节多，适合排查具体某一次请求出了什么问题。但如果你想回答"过去一小时平均延迟是多少""现在有多少请求在跑""错误率是不是突然升高了"，一条条翻日志效率极低——这时候需要的是**已经被汇总好的数字**，这就是"指标"（Metrics）。

Prometheus 是目前最主流的开源监控系统，工作模式是"拉取式"（pull）：

1. 你的应用（本项目）只需要负责：把当前的指标数字暴露在一个固定的 HTTP 接口上（本项目是 `/metrics`），格式是纯文本。
2. Prometheus 服务器（一个独立运行的程序，本项目代码里不包含它，需要单独部署）按照配置的时间间隔（比如每 15 秒）主动来访问这个 `/metrics` 接口，把当时的数字抓回去，存到它自己的时序数据库里。
3. Grafana（另一个独立部署的可视化工具）连接 Prometheus，把存下来的历史数据画成图表、做告警。

也就是说，`observability/metrics.py` 只负责第 1 步——"准备好数字，摆在那让人来拿"，不负责存储历史数据、画图，那些是 Prometheus/Grafana 的工作。

### 2.2 三种指标类型：Counter / Histogram / Gauge

`prometheus_client` 提供了几种指标类型，本项目用到三种：

**Counter（计数器）——只能增加，不能减少**

用来记录"总共发生了多少次"，比如总请求数、总错误数。它的值只会一直往上涨（除非进程重启归零）。你不会拿 Counter 记录"当前有多少个"，因为 Counter 不支持减法。

```python
agent_requests_total = Counter(
    "agent_requests_total",
    "Agent 接收并处理的请求总数",
    ["provider", "model", "status"],
)
```

- 第一个参数 `"agent_requests_total"` 是指标名字，Prometheus 里查询时用这个名字。**命名惯例是加 `_total` 后缀表示这是个只增不减的计数**——这是 Prometheus 社区约定，不是语法强制要求，但强烈建议遵守，否则用别的工具的人看名字会误判类型。
- 第二个参数是这个指标的说明文字（帮助信息，暴露在 `/metrics` 里的 `# HELP` 行）。
- 第三个参数 `["provider", "model", "status"]` 是"标签维度"（labels）——**这是 Prometheus 最强大的地方**：同一个指标名字，可以按标签拆成很多条独立的时间序列。比如：

```python
agent_requests_total.labels(provider="openai", model="gpt-4o", status="success").inc()
agent_requests_total.labels(provider="openai", model="gpt-4o", status="error").inc()
agent_requests_total.labels(provider="anthropic", model="claude-sonnet-4", status="success").inc()
```

这三行各自维护一个独立的计数器。之后你可以在 Prometheus 里查"所有 provider 加起来的总请求数"，也可以只查"`provider="openai"` 且 `status="error"` 的请求数"——标签就是你后续做筛选、分组统计的维度。**`.inc()`** 就是"加 1"（也可以 `.inc(5)` 加任意数）。

**Histogram（直方图）——记录数值分布，尤其适合延迟**

如果只知道"平均延迟是 2 秒"，信息量很有限——可能是所有请求都稳定在 2 秒，也可能是 90% 的请求 0.5 秒完成、10% 的请求要 15 秒（被平均数掩盖了）。Histogram 解决的正是这个问题：

```python
agent_latency_seconds = Histogram(
    "agent_latency_seconds",
    "Agent 完成一次请求的端到端延迟（秒）",
    ["provider"],
    buckets=[0.5, 1, 2, 5, 10, 30, 60],
)
```

`buckets` 定义了一组"桶"的边界。每次调用 `.observe(实际耗时)` 时，Prometheus 客户端库会自动统计："这次耗时落在哪些桶里"——具体规则是**每个桶记录"小于等于这个边界值的请求数量"（累积式）**。比如某次请求耗时 3 秒：

- `≤0.5s` 桶：不计入
- `≤1s` 桶：不计入
- `≤2s` 桶：不计入
- `≤5s` 桶：**+1**（3 秒 ≤ 5 秒）
- `≤10s`、`≤30s`、`≤60s` 桶：也都 **+1**（因为是累积的，凡是边界比 3 秒大的桶都会加）

Prometheus/Grafana 拿到这些桶数据后，可以计算出"95% 的请求在多少秒内完成"（P95 延迟）这种更有意义的统计量，而不只是简单平均数。

`.observe(latency)` 就是喂一个实际观测值进去，让它落到对应的桶。

> **一个 Histogram 在 `/metrics` 里会展开成好几条时间序列**——这是 `prometheus_client` 库的固定行为，不是配置多了。以 `agent_latency_seconds` 为例，Grafana 的 Metric 下拉框里搜出来会看到：
>
> | 后缀 Suffix | 含义 | 用途 |
> |---|---|---|
> | `_bucket{le="X"}` | 累积分桶计数：延迟 ≤X 秒的请求有多少个，`le` = "less than or equal"。`buckets=[0.5,1,2,5,10,30,60]` 会生成 7 条 `_bucket` 序列，再加一条隐含的 `le="+Inf"`（等价于总数） | 配合 `histogram_quantile()` 算 P95/P99 延迟 |
> | `_sum` | 所有观测值（延迟秒数）的总和 | 算平均延迟 |
> | `_count` | 观测次数总数（等价于 `_bucket{le="+Inf"}`） | 算平均延迟、算 QPS |
> | `_created` | 该指标第一次被创建的 Unix 时间戳，`prometheus_client` 给所有 Counter/Histogram/Summary 自动加的元数据 | 很少用到，可忽略 |
>
> 常用查询举例：
> ```promql
> # P95 延迟
> histogram_quantile(0.95, rate(agent_latency_seconds_bucket[5m]))
> # 平均延迟 = sum / count
> rate(agent_latency_seconds_sum[5m]) / rate(agent_latency_seconds_count[5m])
> ```
> 顺带一提，Counter（比如 `agent_requests_total`）同样会自动带一条 `_created`，但不会有 `_bucket`/`_sum`——那两个是 Histogram 独有的。

**Gauge（计量器）——可增可减，记录"当前值"**

```python
active_requests = Gauge(
    "active_requests",
    "当前正在处理中的请求数",
)
```

跟 Counter 的区别是 Gauge 支持 `.inc()` 也支持 `.dec()`，适合记录"当前状态"而不是"累计总量"——比如"当前有多少请求正在处理中"，请求开始时 `+1`，结束时 `-1`。

> 注意：`active_requests` 这个 Gauge 在 `metrics.py` 里**定义了但目前代码里没有任何地方调用 `.inc()`/`.dec()`**——所以它的值永远是 0，`/metrics` 里能看到这一行但数字不会变。如果想让它真正生效，需要在请求开始时 `active_requests.inc()`，结束时（不管成功失败）`active_requests.dec()`，本项目目前没有接这一步。

### 2.3 辅助函数 `record_request()`——把打点逻辑集中到一个函数

```python
def record_request(provider: str, model: str, status: str, latency: float, usage=None):
    """一次 Agent 请求完成时记录所有相关指标。"""
    agent_requests_total.labels(provider=provider, model=model, status=status).inc()
    agent_latency_seconds.labels(provider=provider).observe(latency)

    if usage:
        token_usage_total.labels(type="input").inc(usage.input_tokens)
        token_usage_total.labels(type="output").inc(usage.output_tokens)
        if usage.cache_read_tokens:
            token_usage_total.labels(type="cache_read").inc(usage.cache_read_tokens)
```

这个函数存在的意义：如果每个业务代码调用点都要自己写 4、5 行"更新这个指标、更新那个指标"，很容易漏掉某个指标，或者标签传得不一致。把它们收进一个函数，调用方只需要传业务相关的几个值（`provider`、`model`、`status`、`latency`、可选的 `usage`），"具体要更新哪些底层指标"这个细节被封装起来了。

`usage` 参数是可选的（默认 `None`）——因为失败的请求往往没有真实的 token 用量数据，`record_request(..., status="error")` 调用时就不传这个参数，函数内部 `if usage:` 会跳过 token 统计那几行。

### 2.4 `/metrics` 端点：怎么把这些数字"摆出来给人拿"

```python
from fastapi import Response
from observability.metrics import generate_latest, CONTENT_TYPE_LATEST

@app.get("/metrics")
async def metrics():
    return Response(
        content=generate_latest(),
        media_type=CONTENT_TYPE_LATEST,
    )
```

`generate_latest()` 是 `prometheus_client` 库提供的函数——它会遍历所有已定义的指标（`agent_requests_total`、`tool_calls_total`、`agent_latency_seconds`、`active_requests`、`token_usage_total`，只要在这个 Python 进程里被 `import` 过，就会被自动注册到一个全局注册表里），把它们当前的值序列化成 Prometheus 要求的纯文本格式，类似这样：

```
# HELP agent_requests_total Agent 接收并处理的请求总数
# TYPE agent_requests_total counter
agent_requests_total{provider="openai",model="gpt-4o",status="success"} 12.0
agent_requests_total{provider="openai",model="gpt-4o",status="error"} 1.0

# HELP agent_latency_seconds Agent 完成一次请求的端到端延迟（秒）
# TYPE agent_latency_seconds histogram
agent_latency_seconds_bucket{provider="openai",le="0.5"} 3.0
agent_latency_seconds_bucket{provider="openai",le="1.0"} 8.0
...
```

`CONTENT_TYPE_LATEST` 是这种格式对应的 HTTP `Content-Type`（Prometheus 服务器靠这个 header 识别响应体是它认识的格式）。这个接口本质上就是一个"实时快照"——每次访问都是读取当前内存里各个 Counter/Histogram/Gauge 对象的最新值，不涉及数据库。这也是为什么 Prometheus 需要"定期来拉"：数字都在你的应用进程内存里，进程重启，历史数字就清零了（Prometheus 服务器那边存的历史记录不受影响，因为它早就抓走存起来了）。

### 2.5 实际打点位置：`main.py` 的 `/ask` 接口

```python
@app.post("/ask", response_model=AskResponse)
async def ask_endpoint(req: AskRequest) -> AskResponse:
    start = time.time()
    ...
    try:
        result = await _coordinator.run(req.question, session_id=req.session_id)
        ...
        record_request(
            provider=settings.llm_provider,
            model=settings.llm_model,
            status="success",
            latency=time.time() - start,
            usage=Usage(input_tokens=result.input_tokens, output_tokens=result.output_tokens),
        )
        return AskResponse(...)
    except Exception as e:
        ...
        record_request(
            provider=settings.llm_provider,
            model=settings.llm_model,
            status="error",
            latency=time.time() - start,
        )
        return AskResponse(session_id=req.session_id, error=str(e))
```

`start = time.time()` 记录请求进来的时刻，无论走成功还是失败分支，最后都用 `time.time() - start` 算出这次请求耗费的秒数，喂给 `record_request()`。这样保证**不管请求是成功还是抛异常，`agent_requests_total` 和 `agent_latency_seconds` 都会被更新**——只有这样，"错误率"这个指标才有意义（错误率 = `status="error"` 的数量 / 总数量，如果失败的请求不打点，错误率永远看起来是 0）。

**目前的缺口**：`GET /ask/stream`（SSE 流式接口）没有调用 `record_request()`。原因是这个接口的实现是一个异步生成器，一边生成 LLM 的文字增量一边通过 SSE 推给前端，函数结构上"什么时候算请求真正结束、总共用了多少 token"这个聚合信息，在当前代码里没有被单独收集到一个变量里返回。如果想补上，需要改造生成器，在流结束（无论正常结束还是异常）的地方拿到聚合后的 usage 和总耗时，再调用一次 `record_request()`。

| 指标名 Metric Name | 类型 Type | 中文说明 | English Description | Label 维度 | 状态 |
|---|---|---|---|---|---|
| `agent_requests_total` | Counter | Agent 接收并处理的请求总数 | Total number of requests received and processed by the agent | `provider`, `model`, `status` | ✅ 已接入（`/ask` 成功/失败都会 +1） |

| `token_usage_total` | Counter | 累计 Token 用量 | Cumulative token usage | `type`（input / output / cache_read） | ✅ 已接入（仅成功请求记录，失败时不传 usage） |

## 3. 链路追踪：OpenTelemetry (`opentelemetry`)

### 3.1 追踪要解决什么问题

假设一次 `/ask` 请求处理耗时 8 秒，日志和指标能告诉你"这次请求耗时 8 秒、状态是 success"，但不能直接告诉你**这 8 秒具体花在哪一步**——是 LLM 想了 6 秒，还是调用了某个很慢的工具？如果是多轮对话（Agentic Loop 循环了 3 轮，每轮都可能调用工具），耗时分布就更复杂了。

链路追踪（Tracing）的做法是：把一次请求拆成一棵"时间树"。每一个有意义的子步骤都创建一个"Span"（跨度），记录这个步骤的开始时间、结束时间、以及一些附加信息（属性）。多个 Span 按父子关系嵌套起来，就组成一棵树（术语叫一条 Trace），可视化出来大概是这样：

```
agent_loop（总耗时 8.2s）
├─ turn_0（耗时 3.1s，input_tokens=1200，output_tokens=340，tool_calls=["search_web"]）
│   └─ tool_search_web（耗时 2.6s）      ← 这一步最慢
├─ turn_1（耗时 4.8s，input_tokens=1800，output_tokens=90，tool_calls=[]）
```

一眼就能看出："第 0 轮里调用 `search_web` 工具花了 2.6 秒，是整个请求里最慢的一步"。这种"时间轴 + 嵌套关系"的视角，是日志和指标都提供不了的。

### 3.2 OpenTelemetry 的几个核心概念

OpenTelemetry（简称 OTel）是一个厂商中立的可观测性标准/SDK，不只支持追踪，也支持日志和指标（但本项目只用了它的追踪能力，日志和指标分别用了 `structlog` 和 `prometheus_client`）。理解代码前，先搞清楚几个名词：

- **Span（跨度）**：一个有开始、有结束时间的"操作"记录单元，可以带任意数量的"属性"（attribute，本质是 key-value）。
- **Trace（链路）**：一组有父子关系的 Span 组成的树，代表"一次完整请求"的全貌。
- **TracerProvider**：全局的"工厂"，负责创建 `Tracer`，以及决定 Span 数据最终要"导出"到哪里去（或者根本不导出）。
- **Tracer**：具体用来创建 Span 的对象，通常每个服务/模块拿一个。
- **Exporter（导出器）**：把内存里的 Span 数据发送到外部系统的组件，比如发给 Jaeger、Tempo，或者干脆打印到终端调试。
- **SpanProcessor**：Span 结束时，决定"什么时候、怎么"把它交给 Exporter，本项目用的是 `BatchSpanProcessor`（攒一批再一起发送，比每个 Span 都单独发一次网络请求效率高）。

### 3.3 代码逐行解释：`observability/tracing.py`

```python
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.sdk.resources import Resource


def setup_tracing(service_name: str = "my-agent", otlp_endpoint: str | None = None):
    resource = Resource.create({"service.name": service_name})
    provider = TracerProvider(resource=resource)

    if otlp_endpoint:
        try:
            from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
            exporter = OTLPSpanExporter(endpoint=otlp_endpoint)
            provider.add_span_processor(BatchSpanProcessor(exporter))
            print(f"[Tracing] 链路追踪已启动，导出到：{otlp_endpoint}")
        except ImportError:
            print("[Tracing] 未安装 opentelemetry-exporter-otlp，链路数据不导出")

    trace.set_tracer_provider(provider)


tracer = trace.get_tracer("my-agent")
```

**`Resource.create({"service.name": service_name})`**：如果你只部署了这一个 Agent 服务，这个字段看起来没什么用；但真实场景里，Jaeger/Tempo 通常同时收集好几个不同服务的 Trace 数据（比如"网关服务""Agent 服务""数据库代理"各自都在打点），`service.name` 就是用来在界面上区分"这个 Span 是哪个服务产生的"，本项目固定传 `"my-agent"`。

**`TracerProvider(resource=resource)`**：创建一个"追踪总工厂"，绑定上面的服务名信息。**这一步很关键**——如果完全不调用 `setup_tracing()`，`opentelemetry` 库内部会有一个默认的 `TracerProvider`（叫 `ProxyTracerProvider`，是个"什么都不做"的空实现），这种情况下代码里所有 `tracer.start_as_current_span(...)` 调用都不会报错，Span 对象正常创建、正常用，**但底层根本不会真正记录任何数据、更不会导出**——这是一个很容易踩的坑：代码"看起来在用追踪"，实际上完全是空转。

**`if otlp_endpoint:` 这一段——导出目标是可选的**：如果调用 `setup_tracing()` 时没传 `otlp_endpoint`（或传了空字符串），这段代码整个跳过，`provider` 上没有挂任何 `SpanProcessor`，Span 会被正常创建、正常记录属性，但结束时"没人管"，数据留在内存里最终被丢弃——**代码运行完全正常，不会报错，只是数据不会被导出到任何外部系统**。这样设计的好处是：本地开发、没搭 Jaeger 环境时，代码可以正常跑，不会因为"追踪系统没配置"而导致服务起不来。

真正配了 `otlp_endpoint`（比如 `http://localhost:4317`，本地跑的 Jaeger 或 Tempo 监听的 OTLP gRPC 端口）时：

1. `from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter`——这个 import 放在函数内部（而不是文件顶部），是故意的：`opentelemetry-exporter-otlp-proto-grpc` 是一个**可选依赖**，项目主依赖里没有强制要求装它。如果没装，`import` 会抛 `ImportError`，被下面的 `except ImportError` 捕获，打印一行提示后继续往下走（不影响服务启动）——这是"优雅降级"的写法：追踪导出功能是加分项，不应该因为少装了一个包就让整个服务起不来。
2. `OTLPSpanExporter(endpoint=otlp_endpoint)`：创建一个"发送器"，知道要把数据发到哪个地址，用的协议是 OTLP（OpenTelemetry 定义的标准协议，主流的 Jaeger/Tempo/Grafana 云等都支持接收）。
3. `BatchSpanProcessor(exporter)`：包一层"批量处理"逻辑——Span 结束时不会立刻发一次网络请求，而是先攒在一个内存队列里，凑够一批（或者到了固定的时间间隔）再一次性发送，减少网络开销。
4. `provider.add_span_processor(...)`：把这个"批量处理器 + 导出器"组合挂到 `provider` 上，之后所有 Span 结束时都会经过它。

**`trace.set_tracer_provider(provider)`**：把刚刚配置好的 `provider` 设成"全局默认"——这是一个进程级别的全局单例设置，调用一次即可，之后整个进程里任何地方调用 `trace.get_tracer(...)` 拿到的 Tracer，创建的 Span 都会走这个 `provider` 的逻辑。**这也是为什么 `setup_tracing()` 必须在服务启动时尽早调用**：如果先创建了 Span，之后才调用 `setup_tracing()`，那些先创建的 Span 已经错过了正确配置的窗口。

**`tracer = trace.get_tracer("my-agent")`**：模块顶层创建一个全局的 `tracer` 变量。注意这一行在文件被 `import` 时就执行了，此时 `setup_tracing()` 可能还没被调用——但这**没关系**，因为 `tracer` 对象本身很轻量，它在真正调用 `start_as_current_span()` 创建 Span 的那一刻，才会去看"当前全局的 `TracerProvider` 是什么"，用的是最新状态。所以哪怕别的模块在 `setup_tracing()` 调用之前就 `from observability.tracing import tracer`，也不会有问题——影响的只是"这个 Span 到底会不会被导出"，不影响"能不能正常创建、用"。

### 3.4 怎么用：`start_as_current_span()` 和"嵌套"是怎么自动发生的

```python
with tracer.start_as_current_span("agent_loop") as loop_span:
    loop_span.set_attribute("session_id", session_id or "")
    loop_span.set_attribute("provider", provider.model_name)

    while True:
        with tracer.start_as_current_span(f"turn_{state.turn_count}") as turn_span:
            # ... LLM 调用
            turn_span.set_attribute("input_tokens", turn_usage.input_tokens)
```

`tracer.start_as_current_span("agent_loop")` 返回一个上下文管理器（配合 `with` 使用）。进入 `with` 块时创建 Span 并记录开始时间；退出 `with` 块（正常结束或者抛异常）时自动记录结束时间——你完全不需要手动调用"结束"，`with` 语法帮你做了。

**"as current"是关键词**——OpenTelemetry 在背后用 Python 的 `contextvars` 机制维护了一个"当前活跃 Span 是谁"的隐藏状态。当你在 `agent_loop` 这个 `with` 块**内部**又调用了一次 `tracer.start_as_current_span("turn_0")`，新创建的 `turn_0` Span 会自动检测到"当前活跃 Span 是 `agent_loop`"，于是把自己设成 `agent_loop` 的**子 Span**——这就是父子关系的来源，你不需要手写"这个 Span 的父亲是谁"，只要代码上是嵌套的 `with` 块，父子关系就自动建立了。

`loop_span.set_attribute("session_id", ...)` 就是往这个 Span 上挂一个 key-value 属性，之后在 Jaeger 界面里点开这个 Span，能看到这些属性，方便排查"这次追踪具体是哪个会话、用了哪个 provider"。

### 3.5 一个容易踩的坑：并行执行的地方不能用 `for` 循环包 Span

本项目的工具调用是**并行**执行的（见 `agent_core/executor.py` 的 `asyncio.gather()`）——同一轮里 LLM 如果决定同时调用"查天气"和"查汇率"两个工具，这两个工具是同时开始执行的，不是一个个排队。

如果照着"每个操作一个 Span"的直觉，写成这样：

```python
# ❌ 错误示范：在 run_agent_loop 里用 for 循环包 Span
for tc in tool_calls:
    with tracer.start_as_current_span(f"tool_{tc.name}") as tool_span:
        result = await execute_tool(tc)   # 这里被迫改成了顺序执行
```

这样写虽然看起来每个工具都有了自己的 Span，但**为了让每个 `with` 块能正确记录开始/结束时间，代码逻辑上被迫变成了"一个个顺序等待"**——原本可以同时跑的两个工具，现在变成了先等第一个完全跑完，再跑第二个，白白拖慢了整个请求的速度，这是本末倒置：加可观测性的代码,反而拖慢了被观测的代码。

本项目的正确做法是把 Span **下沉到真正执行单个工具的函数内部**（`agent_core/executor.py` 的 `_execute_one()`），保持外层调度逻辑（`asyncio.gather`）完全不变：

```python
class ToolExecutor:
    async def execute_all(self, tool_calls):
        # Span 不在这里创建，并行调度逻辑完全不受影响
        tasks = [self._execute_one(tc) for tc in tool_calls]
        return list(await asyncio.gather(*tasks))

    async def _execute_one(self, tool_call):
        with tracer.start_as_current_span(f"tool_{tool_call.name}") as tool_span:
            tool_span.set_attribute("tool.name", tool_call.name)
            # ... 真正执行这一个工具
```

`asyncio.gather(*tasks)` 会同时启动所有 `_execute_one()` 协程，每个协程各自独立创建、结束自己的 Span，互不阻塞。这里能正确工作依赖一个事实：OpenTelemetry 的"当前活跃 Span"状态是通过 `contextvars` 实现的，而 `contextvars` 在 `asyncio` 任务之间是**隔离**的（每个 `asyncio.Task` 会拷贝一份创建时刻的上下文），所以多个并发工具各自的 Span 不会互相"看到"对方、也不会搞乱父子关系——每个工具的 Span 都会正确地把 `turn_N` Span（父 Span）当成自己的父亲，即使它们是同时在跑的。

**结论/记忆点**：并行执行的代码，Span 要下沉到"真正执行单个任务"的那一层函数内部去创建，不要在外层的循环/调度代码里包 Span，否则会把并行改成串行。

### 3.6 导出之后去哪看？（本项目没包含，需要额外部署）

`setup_tracing()` 配了 `otlp_endpoint` 之后，Span 数据会通过 OTLP 协议发送出去，但发到哪、怎么看，取决于你在那个地址上部署了什么服务。常见选择：

- **Jaeger**：最经典的开源分布式追踪系统，有自己的 Web UI，可以按 Trace ID 查看完整的时间树、每个 Span 的属性。本地测试最简单的方式是用官方的 all-in-one Docker 镜像，一条命令跑起来，同时监听 OTLP 接收端口和 Web UI 端口。
- **Grafana Tempo**：跟 Grafana 生态整合更紧密，如果已经在用 Grafana 看 Prometheus 指标，Tempo 可以直接在同一个 Grafana 界面里查追踪数据，还能做"指标和追踪互相跳转"。
- 云厂商的 APM 产品（阿里云 ARMS、腾讯云 APM 等）通常也支持直接接收 OTLP 协议数据。

这些都是独立部署的外部系统，本项目代码（`tracing.py`）只负责"按标准协议把数据发出去"，不包含任何这些系统本身的部署配置。

## 4. 三个模块怎么在启动时被"点亮"

三个模块各自都有一个 `setup_xxx()` 函数，必须在服务启动、且在处理任何真实请求之前调用一次，否则相应的可观测能力是"缺失"或"空转"的状态。本项目在 `main.py` 的 FastAPI `lifespan`（生命周期钩子，服务启动/关闭时执行）里统一调用：

```python
from observability.logging import logger, setup_logging
from observability.tracing import setup_tracing
from core.config import settings

@asynccontextmanager
async def lifespan(app: FastAPI):
    global _swarm_save_task

    setup_logging()
    setup_tracing(service_name="my-agent", otlp_endpoint=settings.otel_exporter_otlp_endpoint or None)

    logger.info("server_starting")
    ...
    yield
    ...
    logger.info("server_shutdown")
```

注意几个细节：

1. **先 `setup_logging()`，再 `setup_tracing()`**：这样 `setup_tracing()` 内部如果打印/记录信息，走的已经是配置好的结构化 logger（虽然目前 `tracing.py` 用的是 `print()` 不是 `logger`，但保持这个调用顺序是好习惯）。
2. **`otel_exporter_otlp_endpoint or None`**：这是 `core/config.py` 里定义的一个配置项，默认是空字符串 `""`。因为 `"" or None` 在 Python 里的结果是 `None`（空字符串是"假值"），这一行的作用是把"没配置"（空字符串）统一转换成 `None`，配合 `tracing.py` 里 `if otlp_endpoint:` 的判断——不用担心 `.env` 里这一项没填就传出一个空字符串搞乱逻辑。
3. **`prometheus_client` 没有 `setup_xxx()` 函数**——因为它的 Counter/Histogram/Gauge 对象是在 `import observability.metrics` 的时候就已经创建好、注册到全局表里的，不需要一个额外的"初始化"步骤，只要这个模块被 `import` 过（比如 `main.py` 顶部 `from observability.metrics import ...`），`/metrics` 接口就能拿到它们当前的值。

`core/config.py` 里对应的配置项：

```python
class Settings(BaseSettings):
    ...
    otel_exporter_otlp_endpoint: str = ""   # 不填则链路数据不导出，只在本地"空转"
```

想要真正把链路数据发出去，在 `.env` 里加一行（假设本地用 Docker 跑了 Jaeger，OTLP gRPC 端口是 4317）：

```
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
```

### 5.3 验证追踪（本地不部署 Jaeger 的简化验证）

因为默认没配 `otlp_endpoint`，Span 不会真的发送到任何地方，但可以验证"代码逻辑没崩、Span 正常创建/结束"——最简单的方式是临时在 `setup_tracing()` 里加一个 `ConsoleSpanExporter`（`opentelemetry.sdk.trace.export.ConsoleSpanExporter`，把 Span 直接打印到终端，SDK 自带，不需要额外装包），跑一次 `/ask` 请求，能在终端看到形如：

```
{
    "name": "tool_calculator",
    "context": {"trace_id": "...", "span_id": "..."},
    "parent_id": "...",   # 对应 turn_0 这个父 Span 的 span_id
    "start_time": "...",
    "end_time": "...",
    "attributes": {"tool.name": "calculator"}
}
```

看到 `parent_id` 正确指向了外层 `turn_N` Span，说明父子关系建立对了。这只是本地调试手段，正式验证还是要接一个真实的 Jaeger/Tempo。

## 6. 小结：一张图串起来

```
一次 /ask 请求进来
       │
       ├─▶ logger.bind(session_id=...).info("ask_request_received", ...)     ← 日志：记录"发生了什么"
       │
       ├─▶ tracer.start_as_current_span("agent_loop")                        ← 追踪：开始记录这次请求的时间树
       │       └─▶ start_as_current_span("turn_0")
       │               └─▶ start_as_current_span("tool_xxx")（并行执行的工具，Span 建在 _execute_one 内部）
       │
       ├─▶ record_request(provider, model, status, latency, usage)          ← 指标：更新全局计数器/直方图
       │
       └─▶ 返回响应

与此同时，独立于每次请求：
  GET /metrics  ← Prometheus 服务器定期来拉取指标当前值
  Span 数据（如果配了 otlp_endpoint）← 异步批量发送给 Jaeger/Tempo
```

三个模块相互独立、互不依赖（删掉任何一个，另外两个照常工作），共同覆盖了"发生了什么细节"（日志）、"整体趋势和数量"（指标）、"一次请求内部的时间分布"（追踪）三个不同粒度的问题。
